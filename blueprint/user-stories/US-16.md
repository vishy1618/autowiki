# US-16 — Upload vault to Google Drive

**As a user**, I want my vault files automatically uploaded to Google Drive whenever they change so that my notes are continuously backed up in the cloud.

## Background

This is the first Drive sync story. It covers the OAuth integration, the Drive API client, sync state infrastructure, and the local→Drive upload direction. No download or status UI is included — those come in US-17 and US-18. The feature is entirely headless and config-driven; no UI changes are needed.

Drive sync uses the `drive.file` OAuth scope (access limited to files the app creates). The same `google_client_id` / `google_client_secret` used for sign-in are reused. The Drive scope is added to the login flow at startup when `drive_sync.enabled: true`. A user who logged in before enabling Drive sync must sign out and back in once to grant the new scope.

## Acceptance Criteria

- When `drive_sync.enabled: true`, the Google sign-in OAuth flow requests `https://www.googleapis.com/auth/drive.file` in addition to identity scopes with offline access. The OAuth refresh token is stored in Pebble after the callback.
- On startup, if a refresh token is present and `drive_sync.enabled: true`, the sync manager starts automatically.
- On first start, the manager creates the Drive vault folder if absent, then performs an initial upload reconciliation: every vault file not present in the Drive folder is uploaded. Files already tracked in sync state are skipped.
- Local file changes (create, write, rename, delete) are detected via `fsnotify` and processed within 5 seconds (2 s debounce + upload time).
  - Create / write / rename → file is uploaded to Drive; Drive file ID stored in Pebble.
  - Delete → file is trashed in Drive; state entry removed from Pebble.
- Vault subdirectory structure is mirrored as Drive subfolders inside `drive_sync.vault_folder_name`. Folder IDs are tracked in sync state so no redundant API calls are made.
- Sync errors are logged but do not crash the server or affect chat.

## Architecture Notes

- **Package name**: `internal/drivesync` (not `internal/sync` — that shadows the stdlib `sync` package).
- **Offline access**: Auth must use `oauth2.AccessTypeOffline` when Drive sync is enabled so that a refresh token is issued. The current default is `AccessTypeOnline`.
- **Persisting token source**: The `oauth2.TokenSource` built from the refresh token must write updated tokens back to Pebble on each refresh. A mid-lifetime token refresh followed by a server restart would otherwise leave a stale refresh token in Pebble.
- **`DriveTokenStore` in `store`**: The auth callback (writer) and the sync manager (reader) both need access to the refresh token in Pebble. Rather than coupling them on a raw key string, a `DriveTokenStore` interface lives in `internal/store` and is implemented by `PebbleStore`. Both `auth` and `drivesync` depend on `store` — no cross-package import between them.
- **Folder ID tracking in state**: Drive is not path-based. Each subfolder must be created individually and its ID stored (`drive_sync:folders:<relPath>`) so `Upload` can resolve the correct parent without redundant API calls.
- **Factory function, not wiring in main.go**: `drivesync.New(cfg, db, vaultPath, tokenStore)` owns all internal construction (`PersistingTokenSource`, `DriveClient`, `State`, `Watcher`). main.go calls `New(...)` then `go sm.Start(ctx)` — it has no knowledge of drivesync internals.
- **Token check inside `Start`, not in main.go**: If no refresh token is present (user hasn't signed in since Drive sync was enabled), `Start` logs a clear message and returns. main.go starts the goroutine unconditionally when `drive_sync.enabled: true`; it does not call `DriveTokenStore.GetDriveToken` itself.
- **Single upload worker**: A buffered channel serialises all upload and trash operations. Both the initial reconcile and the live watcher consumer send jobs to the same worker goroutine, preventing duplicate uploads and state corruption when both run concurrently.
- **fsnotify subdirectory race**: When a new subdirectory is created, events for files added immediately inside it can be missed before the watch is registered. After adding a watch on a new directory, the watcher performs an immediate scan of its contents and emits synthetic Create events for any files found.

## Implementation Checklist

### Group 1 — Config + Drive OAuth
_Observable: sign out, sign back in with `drive_sync.enabled: true`, confirm the refresh token is stored in Pebble._

- [ ] Add `DriveSync` struct to `internal/config/config.go`: `Enabled bool`, `VaultFolderName string` (default `"autowiki-vault"`). Add `PollIntervalSecs int` (default `60`) and `ConflictStrategy string` (default `"last_write_wins"`) as placeholders for US-17.
- [ ] Add `DriveTokenStore` interface to `internal/store/store.go`: `GetDriveToken() (string, error)` and `SetDriveToken(refreshToken string) error`.
- [ ] Implement `DriveTokenStore` on `PebbleStore` using key `drive:refresh_token`.
- [ ] In `auth.Handler`, when `drive_sync.enabled`, add `https://www.googleapis.com/auth/drive.file` to OAuth scopes and switch from `oauth2.AccessTypeOnline` to `oauth2.AccessTypeOffline` in `AuthCodeURL`.
- [ ] In `auth.Callback`, when Drive sync is enabled and `token.RefreshToken != ""`, call `DriveTokenStore.SetDriveToken`.
- [ ] Pass `store.DriveTokenStore` into `auth.NewHandler` (new constructor parameter; `nil` when Drive sync is disabled).
- [ ] Tests:
  - When Drive sync is enabled, the OAuth config scopes include `drive.file` and the auth URL contains `access_type=offline`.
  - Callback stores the refresh token via `DriveTokenStore` when one is present in the token response.
  - Callback is a no-op for token storage when Drive sync is disabled.
  - Config loads with `DriveSync` defaults applied correctly.

### Group 2 — Drive API client + vault folder creation on startup
_Observable: start the server with a valid refresh token in Pebble — the `autowiki-vault` folder appears in Google Drive (My Drive root)._

- [ ] Implement `internal/drivesync/token.go`: `PersistingTokenSource` wrapping an `oauth2.TokenSource`. On each `Token()` call, if the underlying source returns a token with a new `RefreshToken`, write it back via `DriveTokenStore`. Constructor: `NewPersistingTokenSource(base oauth2.TokenSource, store store.DriveTokenStore) *PersistingTokenSource`.
- [ ] Implement `internal/drivesync/client.go`: `DriveClient` wrapping `google.golang.org/api/drive/v3`. Constructor accepts a `PersistingTokenSource`.
  - `EnsureFolder(name, parentID string) (folderID string, error)` — finds by name under `parentID` (or Drive root if empty) or creates if absent.
  - `GetStartPageToken() (string, error)` — calls `changes.getStartPageToken`.
- [ ] Implement `internal/drivesync/manager.go`: `SyncManager` and a factory `drivesync.New(cfg Config, db *pebble.DB, vaultPath string, tokenStore store.DriveTokenStore) *SyncManager` that owns all internal construction (`PersistingTokenSource`, `DriveClient`, `State`, `Watcher`). `SyncManager.Start(ctx)` checks for the refresh token first — if absent it logs `"drive sync enabled but no refresh token — sign out and back in"` and returns without error. If present it builds the client, calls `EnsureFolder`, stores the folder ID in memory, calls `GetStartPageToken`, and logs it (state storage comes in Group 3).
- [ ] Wire `SyncManager` into `cmd/server/main.go`: when `drive_sync.enabled: true`, call `drivesync.New(...)` and `go sm.Start(ctx)`. No token check in main.go — that is `SyncManager`'s responsibility.
- [ ] Tests (using a fake HTTP transport):
  - `EnsureFolder` returns the existing folder ID when one matches by name.
  - `EnsureFolder` creates and returns a new folder when none is found.
  - `PersistingTokenSource` writes an updated refresh token back to `DriveTokenStore` when the underlying source returns a new one.
  - `PersistingTokenSource` is a no-op when the refresh token has not changed.
  - `SyncManager.Start` logs and returns without error when no refresh token is present in `DriveTokenStore`.

### Group 3 — Initial upload reconciliation
_Observable: start the server with a fresh sync state — all vault files appear in Drive under the correct subfolder structure._

- [ ] Implement `internal/drivesync/state.go`: `State` backed by `*pebble.DB` (same handle passed from `main.go`; no second Pebble open).
  - `drive_sync:page_token` — start page token for US-17 consumption.
  - `drive_sync:root_folder_id` — Drive ID of the root vault folder.
  - `drive_sync:folders:<relPath>` — Drive folder ID for each mirrored subdirectory.
  - `drive_sync:files:<relPath>` — JSON: `{ driveID, md5, driveModTime, localModTime }`.
  - `drive_sync:last_vault_sync` — RFC3339 timestamp of last successful operation.
  - `drive_sync:last_error` — last error string; empty string when none.
  - Methods: `GetPageToken/SetPageToken`, `GetRootFolderID/SetRootFolderID`, `GetFolder/SetFolder/DeleteFolder`, `GetFile/SetFile/DeleteFile`, `SetLastVaultSync`, `SetLastError`.
- [ ] Add to `DriveClient`:
  - `EnsureFolderPath(relDir string, rootFolderID string, state *State) (folderID string, error)` — walks each path segment, resolving from `State` before calling `EnsureFolder`, writing new folder IDs back to `State`.
  - `Upload(relPath, localPath string, parentFolderID string) (driveFileID string, error)` — creates or updates the file in Drive.
- [ ] Add an upload worker to `SyncManager`: a single goroutine reading from a buffered `uploadJob` channel. A job is either an upsert (relPath + localPath) or a trash (driveFileID). On success it updates `State` and calls `SetLastVaultSync`; on error it calls `SetLastError` and logs.
- [ ] `SyncManager.ReconcileUpload()`: lists all local vault files via `filepath.WalkDir`; for each file with no entry in `State`, enqueues an upsert job. Stores the page token and root folder ID in `State` after `EnsureFolder`.
- [ ] Tests:
  - `State` round-trips set/get/delete for all key types.
  - `EnsureFolderPath` resolves from `State` without an API call on the second invocation.
  - `ReconcileUpload` enqueues upsert jobs for local-only files and skips files already in `State`.
  - Upload worker writes the Drive file ID into `State` after a successful upload.

### Group 4 — Live file watching
_Observable: create, edit, or delete a vault file — Drive reflects the change within 5 seconds._

- [ ] Implement `internal/drivesync/watcher.go`: `Watcher` using `fsnotify`.
  - Recursively watches `VAULT_PATH`: on startup, walks the directory tree and adds a watch for each subdirectory.
  - When a `Create` event arrives for a directory, adds a watch and immediately scans its contents, emitting synthetic `Create` events for any files already present (handles the creation-then-write race).
  - Debounces per file path: 2 s after the last event for a given path, emits a single `FileEvent{RelPath, Op}` where `Op` is one of `Write`, `Create`, `Rename`, `Remove`.
- [ ] Wire the watcher consumer into `SyncManager.Start` after `ReconcileUpload` completes: for each `FileEvent`, enqueue an upsert job (`Write/Create/Rename`) or a trash job (`Remove`) on the upload worker channel.
- [ ] Add to `DriveClient`: `Trash(driveFileID string) error`.
- [ ] Upload worker handles trash jobs: calls `Trash`, removes the `State` file entry on success.
- [ ] Tests:
  - Rapid writes to the same file within the debounce window produce exactly one `FileEvent`.
  - A `Create` event on a new directory triggers a watch and emits synthetic events for pre-existing files inside it.
  - Watcher consumer enqueues an upsert for a changed file and the upload worker updates `State`.
  - Watcher consumer enqueues a trash for a deleted file and the upload worker removes the `State` entry.

### Group 5 — Hardening + sign-off
_Observable: all tests pass; revoke the Drive refresh token — the server logs the error and continues serving chat normally._

- [ ] `SyncManager.Start` catches errors from `EnsureFolder`, `GetStartPageToken`, and `ReconcileUpload`; logs them via `slog` and exits the goroutine gracefully without panicking.
- [ ] Upload worker logs errors with `slog.Error` and calls `SetLastError`; continues processing subsequent jobs rather than exiting.
- [ ] Verify `DriveClient` methods surface meaningful error messages (HTTP status + body snippet) for debugging.
- [ ] Add `ListFolder(folderID string) ([]DriveFile, error)` to `DriveClient` — lists all non-trashed files recursively. `DriveFile`: `{ID, RelPath, ModifiedTime, MD5}`. (Used by US-17 download reconciliation.)
- [ ] Tests:
  - `SyncManager.Start` logs and returns without panic when `DriveClient` returns an error.
  - Upload worker calls `SetLastError` and continues on failure.
