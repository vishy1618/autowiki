# US-21 — Download a vault file

**As a user**, I can ask autowiki to give me a download link for any file in my vault so that I can save it locally without leaving the chat.

## Acceptance Criteria

- When the user asks to download a file, the assistant responds with a markdown link that the browser downloads directly (e.g. `[notes.md](/api/vault/files/notes.md)`).
- Clicking the link downloads the file with the correct filename and MIME type.
- The endpoint is auth-protected — unauthenticated requests receive 401.
- Path traversal attempts are rejected — the resolved path must remain inside `VAULT_PATH`.
- Filenames containing spaces, Unicode, or other special characters are handled correctly in the `Content-Disposition` header (RFC 5987 encoding).
- Binary files (PDFs, images, etc.) are served with the correct `Content-Type` derived from the file extension.
- If the requested file does not exist, the endpoint returns 404.
- The assistant proactively offers download links for binary files (PDFs, images) when the user asks about them, and for text files only when the user explicitly asks to download rather than read inline.

## Design Notes

- The endpoint is `GET /api/vault/files/*path` where `*path` is the vault-relative path (e.g. `notes.md`, `_attachments/photo-20260101-abc123.png`).
- Security: `filepath.Clean` the joined path, then verify it has `VAULT_PATH` as a prefix before opening. Reject if not.
- `Content-Disposition`: use `filename*=UTF-8''<percent-encoded>` (RFC 5987) when the filename contains non-ASCII or special characters; fall back to plain `filename="..."` for ASCII-safe names. A small helper handles this.
- No new LLM tool is needed — the LLM constructs the URL from the vault-relative path it already knows via `list_vault` / `read_page` / `search_vault`.

## Implementation Checklist

### Group 1 — File download endpoint (manually testable via curl / browser URL bar)

Delivers: `GET /api/vault/files/*path` behind auth. After this group you can navigate directly to `http://localhost:8080/api/vault/files/notes.md` while logged in and the file downloads.

- [ ] `contentDisposition(filename string) string` helper in `internal/vault` — returns `attachment; filename*=UTF-8''<percent-encoded>` for non-ASCII/special-char filenames, `attachment; filename="<name>"` for plain ASCII.
- [ ] `ServeFile(w http.ResponseWriter, r *http.Request, relPath string)` on `vault.Manager` — resolves and validates the path (must stay within `VAULT_PATH`), sets `Content-Type` via `mime.TypeByExtension` (fallback `application/octet-stream`), sets `Content-Disposition`, streams with `http.ServeContent`.
- [ ] Unit tests for `contentDisposition` and `ServeFile`:
  - ASCII filename → plain `filename=` header.
  - Unicode / spaces → RFC 5987 `filename*=` header.
  - Path traversal (`../secret`) → rejected.
  - Known extension (`.pdf`) → correct `Content-Type`.
  - Unknown extension → `application/octet-stream`.
- [ ] `GET /api/vault/files/{path...}` route in `internal/server`, auth-protected. Handler extracts the wildcard, calls `vault.Manager.ServeFile`. Returns 404 for missing files, 400 for an empty path.
- [ ] Handler integration tests (`httptest`):
  - Authenticated request for existing file → 200 with correct headers.
  - Unauthenticated request → 401.
  - Non-existent file → 404.
  - Path traversal → 400 or 404.

### Group 2 — LLM integration (manually testable through chat)

Depends on Group 1. Delivers: the assistant generates a working download link when asked. After this group you can type "download my notes.md" in chat and click the link to save the file.

- [ ] Add a "Download links" section to the system prompt in `internal/llm`:
  - Construct links as `[{filename}](/api/vault/files/{vault-relative-path})`.
  - Offer proactively for binary files (PDFs, images, non-text types) when the user asks about them.
  - For text/markdown files, offer only when the user explicitly asks to download rather than read inline.
  - Use `list_vault` or `search_vault` first if the exact path is not already known.
