# US-15 — Search the web and fetch URLs

**As a user**, I can share a URL or ask autowiki to look something up online, and have it fetch and read the content so that knowledge from the web can flow into our conversation and into my vault.

## Acceptance Criteria

- When the user shares a URL, the model fetches and reads it without being asked explicitly.
- When the user asks to look something up (e.g. "find me the latest on X", "what does the docs say about Y"), the model searches the web and fetches the most relevant result.
- The model uses its judgment to decide whether fetched content is worth saving to the vault — it should save substantive articles, documentation, or research, but not transient or low-value pages.
- A status line is shown while searching or fetching so the user knows the model is working.
- JavaScript-rendered pages are a known limitation and do not need to be handled.

## Design Notes

Both tools are Anthropic-native (no external API keys required):

- **`web_search_20250305`** — general queries; costs $0.01 per search.
- **`web_fetch_20250910`** — fetches a specific URL (including PDFs); no extra charge beyond token costs.

The natural flow for a lookup: `web_search` → model picks the best URL → `web_fetch` → model answers and optionally saves to vault.
The natural flow for a shared URL: skip `web_search`, go straight to `web_fetch`.

Both tools are executed server-side by Anthropic. The SSE stream shape is fundamentally different from custom tools:

- Custom tools (`save_to_vault`, `read_page`, etc.): stream ends with a `tool_use` block → Go dispatches → second LLM call.
- Built-in tools: stream emits a `server_tool_use` block, Anthropic immediately executes it, a `web_fetch_tool_result` / `web_search_result` block follows in the **same stream**, model continues and answers — all in one response. No second LLM call needed.

The current `scanStream` only handles `text` and `tool_use` block types. It needs to be extended to recognise `server_tool_use` and emit a `status` SSE event when one is seen. The result blocks (`web_fetch_tool_result`, `web_search_result`) are already consumed by the model server-side and can be skipped by the scanner.

## Implementation Checklist

### Group 1 — LLM: tool definitions

- [ ] Add `web_search_20250305` tool definition to `toolDefinitions` in `internal/llm/llm.go`.
  - Type: `"web_search_20250305"`, name: `"web_search"`, `max_uses: 5`.
- [ ] Add `web_fetch_20250910` tool definition to `toolDefinitions`.
  - Type: `"web_fetch_20250910"`, name: `"web_fetch"`, `max_uses: 5`.
- [ ] Tests:
  - `web_search` tool is present in every `Stream` request.
  - `web_fetch` tool is present in every `Stream` request.

### Group 2 — LLM: system prompt

- [ ] Add instruction: when the user shares a URL, call `web_fetch` on it before responding.
- [ ] Add instruction: when the user asks to look something up online, call `web_search` first, then `web_fetch` on the most relevant result.
- [ ] Add instruction: after reading web content, apply the same vault-write judgment as for any other information — save substantive content, skip ephemeral or low-value pages.
- [ ] Tests:
  - System prompt mentions `web_fetch` and when to use it.
  - System prompt mentions `web_search` and when to use it.

### Group 3 — Chat handler: `server_tool_use` status events

Built-in tools use `server_tool_use` content blocks (not `tool_use`). The scanner must be extended to recognise these and emit a `status` SSE event. No Go dispatch is needed — Anthropic executes the tool and streams the result back automatically.

- [ ] In `scanStream`, handle `content_block_start` with `type: "server_tool_use"`:
  - Record the block index, tool name, and accumulate `input_json_delta` into a JSON buffer (same as `tool_use`).
  - On `content_block_stop` for a `server_tool_use` block, emit a `status` SSE event:
    - `web_fetch`: `{"message":"Fetching <url>…"}` (parse `url` from accumulated JSON).
    - `web_search`: `{"message":"Searching the web…"}`.
  - Do NOT add to `toolCalls` — the agentic loop must not try to dispatch these.
- [ ] In `scanStream`, recognise `web_fetch_tool_result` and `web_search_result` content block types and skip them (no-op).
- [ ] Tests:
  - Given a stream containing a `server_tool_use` `web_fetch` block, `scanStream` emits a `status` SSE event containing the URL.
  - Given a stream containing a `server_tool_use` `web_search` block, `scanStream` emits a `status` SSE event.
  - `server_tool_use` blocks do not appear in `streamResult.toolCalls`.
